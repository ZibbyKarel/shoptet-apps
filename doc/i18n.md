# i18n – `libs/shared/i18n` and the app's message catalogs

Task 17 from `doc/implementation-plan.md`, extended by `TODO.md` item 9 (the
English locale). `libs/shared/i18n` is the **only place in the entire workspace
allowed to import `next-intl`** (enforced by `no-restricted-imports` in the
root `eslint.config.mjs`, see `doc/workspace.md`, "Wrapper layers" section).
FE feature code imports only `@garage/i18n`.

The lib carries the tags `type:util`, `scope:web` (`doc/workspace.md`).
`scope:web` is deliberate here and load-bearing: `apps/garage/api` (`scope:api`)
cannot depend on `libs/shared/i18n`, so `next-intl` has no path into the backend.

The **copy**, though, is not in the lib. It lives in the application, as two
JSON catalogs — `doc/decision/0303-message-catalogs-live-in-the-app-not-in-libs-i18n.md`
explains why it could not be otherwise, and "Where the copy lives" below says
how it is organised. The lib is the runtime; the app supplies the messages.

## What the lib does

1. **Re-exports the Europe/Prague date logic from `libs/garage/shared-types`** under
   the same names (`doc/decision/0003-date-helpers-in-shared-types.md`) —
   `DateOnly`, `todayInPrague`, `isWeekend`, `isCzechPublicHoliday`,
   `czechPublicHolidayOn`, `isBusinessDay`, `monthLockState`, … Feature code
   imports only `@garage/i18n`, never `@garage/shared-types` directly.
2. **Defines what a locale is, and negotiates one** (`lib/locale.ts`) —
   `LOCALES`, `Locale`, `DEFAULT_LOCALE`, `LOCALE_COOKIE`, `LOCALE_LABELS`,
   `isLocale`, `negotiateLocale`. Deliberately free of `next-intl`, because
   both the server and the client error boundary need this answer without
   standing up an intl runtime.
3. **Formats dates per locale** (`lib/date-formatters.ts`) exactly as shown in
   `doc/design/screens/07-lot.png` and `05-admin-window.png` for Czech, and
   in the way English reads for English. The one form `Intl` cannot produce,
   `MONTH_LOCATIVE_CS`, stays in `lib/dates.ts`.
4. **Turns contract error codes into a sentence** in whichever locale's
   catalog it is handed (`lib/errors.ts`).
5. **`IntlProvider`** (`lib/provider.tsx`) — a thin wrapper over
   `NextIntlClientProvider` taking a required `locale` and a required
   `messages`, both resolved once per request in
   `apps/garage/web/src/app/layout.tsx`. The time zone stays fixed at
   `Europe/Prague`: a reservation day is a Prague calendar day whatever
   language you read it in.

## Where the copy lives

```
apps/garage/web/messages/cs.json            280 keys — the source of truth
apps/garage/web/messages/en.json            the same 280 keys, in English
apps/garage/web/messages/messages.spec.ts   the parity guard over both
apps/garage/web/next-intl.d.ts              the key type, augmented from cs.json
apps/garage/web/src/i18n/load-messages.ts   the only place a catalog is read
```

`cs.json` is the source of truth for **keys**, not merely the first
translation. `apps/garage/web/next-intl.d.ts` augments `next-intl`'s
`AppConfig["Messages"]` with `typeof csMessages`, which is how
`useTranslations` gets its namespace and key types: a typo in either is a
compile error. The augmentation is asymmetric on purpose — a key that exists
only in `en.json` is invisible to TypeScript, and only becomes an error at a
reference site. That was verified rather than assumed (`0303`), and it is the
gap `messages.spec.ts` closes.

`load-messages.ts` imports both files statically rather than through a computed
``import(`./${locale}.json`)``: the set of locales is closed, a computed
specifier defeats bundling, and a missing file should be a build error rather
than a 500 on somebody's first page load.

### The parity guard, check by check

`apps/garage/web/messages/messages.spec.ts` compares the catalogs against **each
other**, never against a snapshot. What each check catches:

| check                                                 | what would otherwise happen                                                                     |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| covers every locale the app can negotiate             | a locale added to `LOCALES` with no catalog behind it                                           |
| has every key Czech has                               | next-intl falls back at runtime and an English UI shows a Czech sentence                        |
| has no key Czech does not have                        | dead copy nothing can render, invisible to the type system                                      |
| same ICU arguments as Czech in every message          | `{month}` renamed or dropped in translation — a literal `{month}` on screen, or a missing value |
| no empty message, in any locale                       | a blank label that renders as nothing at all                                                    |
| typographic apostrophes only                          | a straight `'` is an ICU **escape**: `You're` swallows the rest of the message                  |
| translates every contract error code, per locale      | a new `ErrorCode` reaches a user as a raw enum name                                             |
| `OUT_OF_HORIZON` ≠ `RESERVATIONS_LOCKED`              | "not open yet" and "already locked" collapse into one sentence (`doc/decision/0004-*`)          |
| no English message that is still the Czech one        | an untranslated string riding along unnoticed                                                   |
| `const _check: Record<ErrorCode, string> = cs.errors` | a missing Czech error message going undetected until a test run rather than at edit time        |

Two of these exist because two compile-time guarantees were deliberately given
up when the catalogs became JSON in an app, and **this is where they now
live**:

- `libs/shared/i18n/src/lib/errors.spec.ts` can no longer see the real catalogs (a lib
  may not import from an app), so its `ERROR_CODES` fixture is derived from
  `ERROR_CODES` itself and its coverage check is vacuous by construction. The
  per-locale "translates every contract error code" test above is the real
  check — and it is broader than what was lost, because the old one never saw
  English.
- The deleted TypeScript catalog declared
  `interface CzechErrorMessages extends Record<ErrorCode, string>`, which made
  "every contract error code has a Czech message" a _compile-time_ guarantee.
  JSON has no interfaces; the inert `_check` assignment at the bottom of
  `messages.spec.ts` restores it, and works only because
  `apps/garage/web/tsconfig.spec.json` includes `messages/**/*.spec.ts` in the
  typecheck program. Narrow that include and the guarantee goes silently.

The "still Czech" check carries an eight-entry `SHARED` allowlist of values
that are legitimately byte-identical between the catalogs — the product name
`Garage`, two bare `{date}` placeholders, an em dash, and four English
words already used as labels in the Czech UI (`Admin`, `E-mail`). It was
reviewed entry by entry. A ninth entry means either the translation regressed
or the allowlist is being used to hide it.

Two deliberate exceptions, both so the copy stays faithful key by key rather
than internally tidy:

- `lot.legendWaitlist` keeps the loanword **"waitlist"**, because the Czech
  itself reads `waitlist / editace`. Everywhere else `fronta` is "queue".
- `#{position}` renders the Czech ordinal `{position}.` in
  `lot.queuePosition` and `bulk.badgeQueued`: English cannot render a bare
  ordinal from a number the way Czech does with a trailing period. Outside a
  plural argument, `#` is a literal in ICU — verified against
  `intl-messageformat`, not assumed.

### A known cs-side split — do not "fix" it in one catalog

`cs.json` renders one domain concept with two Czech words, and English inherits
the split: `lot.groupLabel`'s `Skupina {group}` becomes `Group {group}`, while
`admin.spotsColumnGroup`'s `Kategorie` becomes `Category` — the same thing a
spot belongs to, named twice. In the other direction, `nav.administration`'s
`Správa` and `admin.eyebrow`'s `Administrace` are two Czech words that collapse
to one English `Administration`.

Both are inherited from the source of truth and were deliberately **not**
corrected in English only. Unifying either pair means changing `cs.json`
first — a product copy decision — and then `en.json`. Changing one catalog
alone breaks the pairing that makes the two readable side by side.

## How the locale is chosen

For one request, in `apps/garage/web/src/app/layout.tsx` via
`apps/garage/web/src/i18n/resolve-locale.ts`:

1. the `NEXT_LOCALE` cookie (`LOCALE_COOKIE`), if its value is a shipped
   locale — an explicit choice, so it wins outright;
2. otherwise `Accept-Language`, in quality order: **`cs` for Czech and for
   Slovak**, `en` for any other named language, and `cs`
   (`DEFAULT_LOCALE`) for a header that is absent, wildcard-only or malformed.

The Slovak rule is a product decision, not an approximation: the two languages
are mutually intelligible and a half-translated Slovak catalog would be worse
than either. The decision itself is `negotiateLocale` in `lib/locale.ts`, which
the client error boundary (`apps/garage/web/src/app/global-error.tsx`, no layout above
it) also calls against `navigator.language`.

The result becomes `<html lang>`, the catalog handed to `IntlProvider`, and the
locale `generateMetadata` reads its title and description in.

The **switcher** is two radio-style entries in the user-avatar menu under a
`nav.language` header (`apps/garage/web/src/shell/top-bar/top-bar.tsx`). Their labels
come from `LOCALE_LABELS` and are endonyms — `Čeština`, `English` — because a
visitor who has landed on the wrong language needs to recognise their own.
`apps/garage/web/src/shell/top-bar/use-locale-switch.ts` writes the cookie
(`path=/`, a year, `SameSite=Lax`, no `Secure` so local plain-HTTP dev works,
value lowercase because `isLocale` is case-sensitive) and calls
`router.refresh()`, which re-runs the server layout. There is **no locale URL
segment and no next-intl middleware** —
`doc/decision/0302-the-locale-is-a-cookie-not-a-url-segment.md`, which also
records the upgrade path if shareable per-language URLs are ever wanted.

`apps/garage/web-e2e/src/locale.spec.ts` is the only spec in the browser suite that
does not run in Czech: it proves detection per browser language, and that an
English choice survives a reload **and** a navigation while the browser keeps
asking for Czech in every request header.

## Date formatting

`createDateFormatters(locale)` returns the eight formatters for one locale,
memoised per locale (`Intl` objects are expensive enough to show up in a table
of thirty rows). Components call `useDateFormatters()`, which reads the locale
off the provider. Pure view modules — `apps/garage/web/src/lot/lot-view.ts`,
`apps/garage/web/src/shell/admin/window-banner/window-view.ts` — are not components
and take a `DateFormatters` as their last parameter instead, which is also what
lets their tests assert both languages with no React tree.

| method                  | `cs`                    | `en`                         | month form             |
| ----------------------- | ----------------------- | ---------------------------- | ---------------------- |
| `fullDate(date)`        | `pondělí 28. září 2026` | `Monday, September 28, 2026` | genitive               |
| `dayMonthAndYear(date)` | `28. srpna 2026`        | `August 28, 2026`            | genitive               |
| `dayAndMonth(date)`     | `25. srpna`             | `August 25`                  | genitive               |
| `monthAndYear(date)`    | `srpen 2026`            | `August 2026`                | nominative             |
| `monthName(month)`      | `srpen`                 | `August`                     | nominative, standalone |
| `monthLocative(month)`  | `srpnu`                 | `August`                     | locative (cs only)     |
| `weekdayName(date)`     | `pondělí`               | `Monday`                     | —                      |
| `year(year)`            | `2026`                  | `2026`                       | —                      |

Czech declines month names, and `Intl`/next-intl only produce the genitive
when `day` is part of the same formatting call — hence separate methods with
separate option objects instead of one parameterized one. `dayMonthAndYear`
(Task 27, for the reservation-window card's "dnes je 28. srpna 2026") is its
own `Intl` call rather than `fullDate` with the weekday cut off: slicing a
locale-formatted string apart is exactly what `Intl` exists to avoid. The
detailed reasoning and a verified example (August, where the nominative and
genitive differ, unlike September, where they coincide) is in
`doc/decision/0024-czech-month-declension-genitive-vs-nominative.md`.

`monthLocative` is the one that is not `Intl` at all for Czech. CLDR carries
two Czech month forms — the `format` (genitive) and the `stand-alone`
(nominative) — and the locative is neither, so `MONTH_LOCATIVE_CS` in
`lib/dates.ts` is a hand-written twelve-entry table, pinned by
`dates.spec.ts`. It is **Czech-only because English declines nothing**: for
`en` the method returns the standalone month name, which is already the form
that reads after "in". Out of range it throws `RangeError` in both locales —
this value lands in the middle of a sentence, where an empty string would be a
silent hole instead of a loud caller bug.

The input is always a `DateOnly` (`YYYY-MM-DD`, a calendar day with no
timezone) — never an instant. The methods internally convert it to UTC
midnight and format with `timeZone: 'UTC'`, so the displayed day is never
shifted by the Europe/Prague zone or a daylight-saving transition. That `UTC`
is unrelated to the `Europe/Prague` zone on `IntlProvider`.

## Error codes

`createErrorTranslator(locale, messages)` (`lib/errors.ts`) returns a
`(code: ErrorCode) => string` for one locale's catalog, covering all twelve
codes in `ERROR_CODES` (`libs/garage/contract/src/schemas/errors.ts`,
`doc/contract.md`). It exists for the plain-TypeScript callers that have a
catalog in hand but no React context; inside a component,
`useTranslations('errors')` reads the catalog already on the provider. Both go
through the same next-intl ICU resolution, so they cannot drift.

Completeness is **not** asserted in the lib. The catalog is now a parameter and
there is more than one of them, so the check that a code has a message in
_every_ locale lives where every locale is visible at once:
`apps/garage/web/messages/messages.spec.ts` (see "The parity guard", above). That
also carries the compile-time assertion that `cs.errors` satisfies
`Record<ErrorCode, string>`.

`OUT_OF_HORIZON` and `RESERVATIONS_LOCKED` deliberately have distinct
sentences in both languages — the first says "not open yet", the second
"already locked" (`doc/decision/0004-*`); the parity spec checks the
distinction per locale rather than only that the strings differ.

## Holidays and weekends for the date bar

`isWeekend`, `isCzechPublicHoliday`, `czechPublicHolidayOn` and `isBusinessDay`
are re-exported from `libs/garage/shared-types` with no behavior change — the 148
tests of the algorithm (fixed holidays + Easter per Meeus/Jones/Butcher) live
there and **are not repeated here**.

`czechPublicHolidays` — the function that returns a whole year's table — is
**not** among them, and it is not withheld here: `libs/garage/shared-types`' own
barrel stopped publishing it. The re-export mandated by
`doc/decision/0003-*` is a wholesale `export * from '@garage/shared-types'`,
so this lib's surface is whatever that one is, by construction, and cannot
drift from it. What the date bar needs is a question about _one_ day, which is
what the four names above answer; a caller wanting the year would be rebuilding
`isCzechPublicHoliday` out of an array. That the list published to the browser
is the smaller one is the point — anything `libs/garage/shared-types` exports lands in
the browser bundle through this barrel. `libs/shared/i18n`'s own tests
(`shared-types-reexport.spec.ts`) only verify that the re-export actually works
(one fixed holiday, one movable one, one regular business day), not that the
algorithm itself is correct — Task 3 already proved that.

## next-intl: why and exactly how

- **`IntlProvider`** wraps `NextIntlClientProvider` with the `locale` and
  `messages` it is given and a fixed `timeZone={PRAGUE_TIME_ZONE}`. Both props
  are required: the locale is resolved once per request on the server and
  handed down through `apps/garage/web/src/app/providers.tsx`, never guessed inside a
  component. `now` is the only overridable prop, purely so tests can pin a
  deterministic clock — production call sites omit it.
- **The catalog type crossing into the app is structural**, not next-intl's
  `AbstractIntlMessages`: `AppMessages` is `Record<string, unknown>`, because a
  wrapper that re-exported the wrapped package's type would put `next-intl`
  back in the app's type surface — the thing the wrapper rule exists to
  prevent. The _keys_ are typechecked at the call sites instead, through the
  `AppConfig["Messages"]` augmentation in `apps/garage/web/next-intl.d.ts`. A
  `declare module` is a type augmentation and not an import, which is why that
  file does not breach the wrapper rule; `web:lint` confirms it on every run.
- The barrel (`src/index.ts`), besides its own API, also re-exports
  `useTranslations`, `useFormatter` and `useLocale` from next-intl —
  components under `IntlProvider` can therefore call them via
  `@garage/i18n` and never need a direct `next-intl` import of their own,
  which would bypass this lib as the sole allowed place.
- **There is still no `i18n/request.ts` / `getRequestConfig`**
  (`next-intl/server`), and two locales did not change that. The reason is now
  a different one: the application resolves the locale itself — a cookie and a
  header, read in the root layout, which is already dynamic because it
  `await auth()`s — and hands the catalog to a client provider. next-intl's
  server entry point exists to feed its own request-scoped configuration and
  its routing/middleware, and this app runs neither
  (`doc/decision/0302-*`). If a locale URL prefix is ever adopted, that entry
  point goes in as part of the same change.
- Jest in `libs/shared/i18n` has to transpile both `next-intl` and `@orpc/contract`
  (both ESM-only). Both package sets are named in `jest.preset.js`'s shared
  `ESM_ONLY_PACKAGES` list — this project's copy was the longest of the eleven
  and is what the union was built from
  (`doc/decision/0297-the-esm-jest-transform-block-lives-in-jest-preset-js.md`,
  following `doc/decision/0020-*`); what stays in
  `libs/shared/i18n/jest.config.cts` is only the `babel-jest` `.mjs` entry and
  `moduleFileExtensions`, neither of which is shareable across projects with
  different transformers. `errors.spec.ts` runs under `@jest-environment node`
  because `@garage/contract` pulls in `@orpc/client`, which references
  `TransformStream`, which jsdom does not provide — the original reasoning is
  in `doc/decision/0025-next-intl-esm-jest-transform.md`.

## Deliberately missing

- **Locale-based URL routing** — no `[locale]` segment, no next-intl
  middleware, no per-language shareable link. Decided, with its upgrade path,
  in `doc/decision/0302-*`.
- **A third locale.** Adding one is a JSON file, an entry in `LOCALES` and a
  line in `load-messages.ts`; nothing in `libs/shared/i18n` would change. Slovak
  specifically is _not_ one, on purpose — a Slovak browser gets the Czech UI.
- **Translated URLs, ICS copy and API messages.** Route segments are English
  identifiers (`doc/decision/0298-*`), the calendar feed's Czech copy lives in
  `libs/garage/calendar-export` (`doc/decision/0082-*`), and the API's error
  `message` field is never UI copy — the frontend keys off `code`.
- **Any locale-aware pluralization in the lib's API.** ICU handles it in the
  catalogs, where four messages already use `plural` (Czech's `one`/`few`/
  `other` against English's `one`/`other`), and the parity spec checks that
  both locales use the same arguments.
